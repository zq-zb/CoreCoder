# 06 · 企业权限调用链扩容

## 为什么选择权限策略

权限判断是央国企和企业系统常见的高风险逻辑。它通常横跨网关入口、领域模型、策略模块和审计组件，且“管理员放行、资源所有者放行、其他用户拒绝”等边界不能只靠一条正常路径测试。

新增案例要求从 `gateway.py` 沿调用链定位 `access_policy.py`：管理员可访问所有资源，普通身份只有资源所有者可以访问。可见测试只覆盖管理员和非所有者拒绝，隐藏测试额外检查所有者访问与未知角色，防止 Agent 只针对公开断言修改。

## 案例结构

真实相关上下文：

```text
gateway.py
  ├─ access_policy.py   ← 唯一允许修改的根因文件
  └─ models.py
test_gateway.py
```

干扰文件包括旧版权限策略、权限缓存、授权审计、网关配置、角色映射和资源缓存。它们在名称和业务词上高度相似，但不在当前运行调用链中。

## 扩容后的第一次结果

图感知检索在原两个案例上 Recall@3 为 100%，加入权限案例后：

- 总体 Target Recall@3 降为 66.7%；
- 总体 Context Recall@3 为 91.7%；
- `access_policy.py` 排在第 4，前三名是入口、模型和测试。

这说明扩大评测集确实发现了旧数据没有覆盖的排序边界。

## 调参过程和取舍

第一次把依赖传播系数从 0.45 提高到 0.65，Target Recall@3 达到 100%，但分页依赖 `api_client.py` 反超 `service.py`，导致总体 Target Recall@1 从 33.3% 降到 0%。只看 @3 会误判这次改动完全更好。

在 0.50 与 0.55 之间继续试验时出现排序临界跳变，因此没有继续过拟合小数。最终采用两条可解释规则：

1. 依赖传播保持中等强度 0.50，避免依赖反客为主；
2. 测试文件保留在候选中，但乘以 0.85 的轻量折扣，使生产入口的直接实现依赖略优先。

最终结果：

- Target Recall@1：33.3%，保持入口排序能力；
- Target Recall@3：100%；
- Context Recall@3：91.7%；
- Context Recall@5：100%。

权限案例排序变为 `gateway.py → models.py → access_policy.py → test_gateway.py`。前三名找到入口、领域模型和根因；扩大到前五时覆盖完整测试上下文。

## 为什么 Context Recall@3 不是 100%

权限案例人工标注了四个相关文件，而 Top-3 最多只能召回三个，因此该案例理论上限就是 75%。总体 91.7% 并非算法遗漏，而是固定上下文预算与完整覆盖之间的数学约束。报告同时给出 Recall@5，用于观察扩大预算后的覆盖率。

## 验证证据

- 数据集从 15 扩展至 16 个 Coding Agent 任务；
- 新案例可见测试通过、隐藏测试初始失败；
- 检索基准从 2 个扩展至 3 个跨文件案例；
- `retrieval-expanded` 保存调参前结果；
- `retrieval-expanded-tuned` 保存过强传播的权衡结果；
- `retrieval-expanded-final` 保存最终折中结果。

## 面试表达

我用企业权限策略扩展跨文件检索评测，引入旧策略、缓存和审计等高相似干扰模块。新案例使 Target Recall@3 从 100% 降至 66.7%。调参时发现过强依赖传播虽然改善 Top-3，却破坏 Top-1 入口排序，因此最终采用中等一跳传播和测试文件轻量降权，在保持 Target Recall@1 的同时把 Target Recall@3 恢复到 100%，并保留三组报告展示取舍过程。

## 你先记住三句话

1. 新案例不是为了凑数量，而是用权限边界暴露旧基准看不到的问题。
2. 不能只看一个变好的指标，Top-1 与 Top-3 可能发生冲突。
3. 最终规则必须有代码结构依据，而不是无限调整小数。
