# CoreCoder 可观测性与 CI 质量门禁

## 为什么不是“加日志就算可观测”

日志适合回答某一次调用发生了什么；指标适合回答系统整体是否正在恶化；事故报告适合回答一次业务事件最终如何收敛。三者关注的粒度不同：

- 审计日志：工具级，关联 `task_id`，记录参数脱敏结果和输出摘要；
- 任务指标：系统级，观察积压、成功率、重试和租约健康；
- 事故报告：业务级，把 CI 证据、任务执行、改动和验收关联起来。

## 当前指标

`corecoder.metrics` 从 SQLite 任务台账生成快照：

- 各状态任务数；
- 终态任务成功比例；
- 总执行尝试次数；
- 发生过重试的任务数；
- 已过期但尚未回收的租约数；
- 最老待处理任务的等待时间。

这些指标只使用固定状态标签，没有把 `task_id`、仓库或用户名放进标签，避免生产监控中的高基数问题。

## 如何运行

Prometheus 文本：

```powershell
.\.venv\Scripts\python.exe -m corecoder.metrics --store .corecoder\tasks.db
```

JSON：

```powershell
.\.venv\Scripts\python.exe -m corecoder.metrics --store .corecoder\tasks.db --format json
```

当前提供的是采集出口，不会自行启动 HTTP 服务。部署时可以由 Prometheus textfile collector、定时任务或现有监控 Agent 采集，避免为了演示额外常驻一个 Web 服务。

## 建议告警语义

- `expired_leases > 0`：Worker 可能失联或回收器没有正常运行；
- 最老待处理时间持续上升：消费能力不足或 Worker 停止；
- 成功比例在足够样本下持续下降：模型、工具或仓库环境发生退化；
- 重试任务快速增加：外部 MCP、测试环境或 Worker 稳定性异常。

不能只凭一次瞬时值告警；生产环境应配置持续窗口，并设置最小样本数。

## CI 自动验收

仓库 CI 新增独立的 `industrial-smoke` Job，在不使用模型 API 和外部 GitHub 数据的情况下执行：

1. 五类故障演练；
2. CI 故障修复端到端闭环；
3. 小规模多 Worker 队列正确性基准；
4. 无论成功失败都上传验证报告，保留 14 天用于复盘。

它与跨平台单元测试分开，因此可以区分“代码函数回归”和“工业关键路径退化”。当前 Action 使用版本标签，进一步强化供应链安全时应把第三方 Action 固定到审核过的提交 SHA。

## 开发过程中发现的问题

首次加入只读权限时，YAML 插入位置不正确，导致 `pull_request` 被缩进到 `permissions` 下。这不会表现为 Python 测试失败，却会让 PR 触发器失效。通过完整读取生成后的 Workflow 发现并修正，说明流水线配置本身也必须接受语法检查和实际运行验证。

指标模块最初同时从 `corecoder.__init__` 顶层导出，并支持 `python -m corecoder.metrics`。Python 运行子模块前会先加载包，导致指标模块被加载两次并产生 `runpy` 警告。指标作为独立运维入口没有顶层导出的必要，因此移除包级重导出，保持 CLI 输出干净。

## 面试表达

> 我按工具调用、运行态和业务事故三个层次设计可观测证据：JSONL 审计回答单次动作，低基数任务指标观察积压、成功率、重试和租约，事故报告关联 CI 证据与修复验收；并在 CI 中设置独立工业冒烟门禁，自动保存故障演练和性能报告。
