# 阶段 11：真实检索实验、负结果与运行时引导

## 1. 第一次实验为什么无效

使用 DeepSeek 对权限调用链案例执行 `retrieval off/on`。两组均通过隐藏测试，但开启组没有调用 `repository_search`。最初的任务直接给出 `gateway.py`，模型没有自主检索的必要，因此不能用该结果证明检索有效或无效。

随后将任务改为只提供业务现象与 `AccessRequest`、`can_access` 代码符号，不再泄露文件路径。离线检索仍将 `models.py`、`access_policy.py`、`gateway.py` 排在前三，说明任务具有可检索线索。

## 2. 修订后的真实 A/B 结果

| 指标 | retrieval off | retrieval available |
|---|---:|---:|
| 隐藏测试 | 通过 | 通过 |
| 工具调用 | 14 | 14 |
| 输入 Token | 26,933 | 31,994 |
| 输出 Token | 1,622 | 2,157 |
| 耗时 | 15.05s | 19.78s |
| repository_search 调用 | 0 | 0 |

两组数据集指纹一致。开启组多消耗 5,061 输入 Token、535 输出 Token，慢 4.74 秒，但由于检索从未实际执行，而且每组只有一次结果，不能把差异归因于检索。

项目没有把这个负结果包装成性能提升，而是新增评测对比器，自动检查：

- 模型、供应商、数据集指纹是否一致；
- 两组运行数量是否一致；
- 每组是否至少有三次结果；
- 候选组是否真的调用检索；
- 费用不可用时是否退回 Token 指标。

## 3. 为什么“工具可用”不等于“模型会用”

DeepSeek 两次都优先使用 Bash、Glob 或 Read 工具遍历仓库。工具 Schema 和提示规则只是软约束，不同模型的工具偏好不同。仅注册工具无法保证实验真正覆盖该能力。

因此将策略拆成三档：

- `off`：不向 Agent 提供检索工具；
- `available`：提供工具，由模型自主选择；
- `guided`：运行时要求第一次仓库检查先单独执行检索。

guided 模式不仅修改提示词。若模型先调用 Bash、Glob、Grep、Read、Edit 或 Write，运行时返回策略拒绝；若同一轮并行请求检索和读取，也会拒绝，因为读取并没有使用检索结果。只有检索单独完成后，后续操作才正常执行。

## 4. 报告隐私

原始真实模型报告包含模型回复和本机临时工作区路径，因此只保留在本地并由 `.gitignore` 排除。公开仓库只提交不含代码正文的聚合对比报告。

同时修复评测器：今后的任务事件、失败原因、模型回复和验收输出会把绝对目录替换为 `<workspace>` 或 `<run_root>`，避免公开报告泄露 Windows 用户名。

## 5. 作业过程中的错误

1. 首次读取 discount 和 pagination 案例时使用了旧目录名，两个 `Get-Content` 失败。通过 `rg` 重新定位为 `03_discount` 和 `07_pagination`，未修改文件。
2. 实现 guided 策略时，一个多文件补丁缺少正确的文件块边界，补丁校验失败。用 `git status` 确认没有部分写入后，将修改拆成多个小补丁完成。

## 6. 面试表达

我用真实 DeepSeek 做检索 A/B 时发现，模型即使获得工具也没有实际调用。为避免产生虚假结论，我先修正泄露文件路径的任务，再开发报告对比器自动识别样本不足、元数据不一致和能力未覆盖。随后将检索策略拆成 off、available、guided，并在运行时执行工具顺序约束，解决不同模型不遵循软提示的问题。原始报告留在本地，公开结果经过路径脱敏。
