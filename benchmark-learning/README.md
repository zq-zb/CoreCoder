# CoreCoder 离线性能基线

## 测试目标

这项基准只测 SQLite 任务台账和并发 Worker 协调开销，不测大模型推理速度，也不代表完整 Coding Agent 每秒能完成 129 个任务。

固定流程：

1. 8 个线程并发提交 200 个带唯一幂等键的任务。
2. 8 个 Worker 并发原子领取并立即写入成功结果。
3. 记录入队吞吐、处理吞吐和每次领取事务的 P50/P95 延迟。
4. 检查是否发生重复领取。
5. 16 次并发提交同一幂等键，检查最终是否只有一个任务 ID。

## 2026-09-07 单轮探索结果

- 200/200 完成。
- 重复领取：0。
- 幂等唯一任务数：1。
- 入队吞吐：346.77 tasks/s。
- 处理吞吐：129.90 tasks/s。
- 领取延迟 P50：7.594 ms。
- 领取延迟 P95：77.223 ms。
- 基准内部总耗时：3.993 秒。

相同参数第二次运行曾达到 192.68 tasks/s、P95 22.135 ms，说明单轮数据波动较大，不能挑选最好结果作为结论。

## 三轮正式基线

使用 200 任务、8 Worker 连续运行三轮：

- 三轮全部通过正确性检查。
- 处理吞吐中位数：84.27 tasks/s。
- 处理吞吐范围：82.26～175.25 tasks/s。
- 最差领取延迟 P95：134.530 ms。
- 重复领取：0。
- 幂等重复提交最终唯一任务数：1。

波动说明当前 SQLite 多写线程会受到写锁竞争、Windows 文件系统和线程调度影响。这个结果不是为了证明“性能很好”，而是建立后续优化或替换存储时的比较起点。

## 如何复现

```powershell
.\.venv\Scripts\python.exe -m corecoder.benchmark --tasks 200 --workers 8 --repeat 3
```

报告记录操作系统、Python 和 SQLite 版本。比较两次结果时必须使用相同任务数、Worker 数和相近机器环境。

## 如何解释

可以说：

> 我为任务存储建立了可重复的三轮离线并发基线。在每轮 8 Worker、200 个轻量任务条件下，事务领取没有发生重复消费，并发幂等提交只生成一条任务；报告吞吐中位数、范围和最差 P95 延迟，并观察到 SQLite 写锁竞争带来的波动，作为未来优化或替换存储的比较基线。

不能说：

> Coding Agent 每秒能完成 129 个代码任务。

基准中的任务没有执行模型推理、代码修改和测试，数字只代表任务协调层。

## 当前不足

- 当前只有三轮本机运行，样本量仍有限。
- 没有包含磁盘繁忙、长事务和数据库损坏场景。
- 没有测不同 Worker 数下的扩展曲线。
- SQLite 单机结果不能推导到多节点部署。
- 完整 Agent 性能还需要单独测模型延迟、工具耗时和测试耗时。
