# 05 · 依赖图感知检索

## 先让基准变难

原始两个案例各只有三个文件，Recall@3 达到 100% 几乎等于列出整个仓库。为避免指标虚高，本阶段加入了十个不会参与真实调用链、但名称和内容与任务相似的模块，例如旧版结算、价格缓存、分页监控、token 缓存和页面序列化。

加入干扰后，困难基线下降为：

| 指标 | 困难基线 @3 | 图感知优化 @3 |
|---|---:|---:|
| 修改目标召回率 | 50.0% | 100.0% |
| 上下文召回率 | 66.7% | 100.0% |

折扣案例的真正根因 `pricing.py` 被挤出前五；分页依赖 `api_client.py` 下降到第五。这证明单纯依靠文件名和词频会受到同名旧模块、监控和辅助文件干扰。

## 优化方案

索引构建时额外提取 Python `import` 和 `from ... import ...`，形成文件之间的模块引用边。完成词法打分后，让高相关候选把一部分分数传播给它直接导入的文件：

```text
任务词法命中 checkout.py
          ↓ checkout.py 明确 import pricing
      提升 pricing.py
```

只传播一跳，不递归展开完整依赖图。这样既能发现入口背后的实现，又避免沿依赖关系把整个仓库重新加入上下文。结果中会显示 `依赖链:checkout.py` 等理由，保持可解释性。

## 为什么没有直接把目标文件提升到第一

任务明确提到 `checkout.py`，入口文件排第一是合理的。真实排障流程通常先阅读入口，再沿调用关系定位根因。目标不是让隐藏答案永远排第一，而是在很小的 Top-K 预算内覆盖完整调用链。

优化后：

- 折扣案例：`checkout.py → test_checkout.py → pricing.py`；
- 分页案例：`service.py → api_client.py → test_service.py`。

前三个文件均为人工标注的相关上下文，没有靠增加 K 掩盖排序问题。

## 证据文件

- `evals/reports/retrieval-hard/`：加入干扰文件后的词法困难基线；
- `evals/reports/retrieval-graph/`：加入一跳依赖传播后的结果；
- `tests/test_repository.py`：验证被入口导入的模块获得依赖链理由；
- `evals/cases/03_discount/workspace/`、`07_pagination/workspace/`：可复查的干扰文件。

## 当前局限

1. 当前只解析 Python 风格 import，还没有覆盖 Java、Go、TypeScript 等语言；
2. 相对导入、动态导入和运行时注册暂未形成准确依赖边；
3. 只有两个跨文件案例，结果仍不足以证明对所有仓库有效；
4. 每次检索会重建内存索引，中型仓库频繁查询时需要缓存与失效机制。

这些局限会保留在项目说明中，避免面试时把有限实验夸大成通用代码搜索平台。

## 开发中出现的错误

第一次添加干扰文件时，补丁调用末尾误写了无效参数，工具在解析阶段报 `SyntaxError`。检查后确认补丁没有产生部分文件，再重新执行完整补丁。这个错误属于开发工具调用格式问题，与检索算法无关，但仍记录下来，体现失败后先确认副作用再重试的习惯。

## 面试表达

我先用同名旧模块、缓存和监控文件构造困难检索集，使 Context Recall@3 从 100% 降至 66.7%，验证词法排序确实会被工程噪声干扰；随后从源码提取 import 依赖边，对高相关入口的一跳依赖进行分数传播，在不增加 Top-K 的情况下将 Target 和 Context Recall@3 恢复到 100%，并保留逐结果的依赖链解释。

## 你先记住三句话

1. 先加干扰文件让指标下降，才知道算法哪里不足。
2. 代码仓库不只是文本集合，还存在真实调用和依赖关系。
3. 优化后仍只返回前三个相关文件，没有靠扩大上下文换成绩。
