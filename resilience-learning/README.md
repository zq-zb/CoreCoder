# CoreCoder 故障演练学习笔记

## 1. 为什么单元测试还不够

单元测试通常验证一个函数在给定输入下是否正确；故障演练验证的是：多个组件组合后，系统遇到异常能否在有限时间内收敛到可解释状态。

本阶段没有模拟“看起来像故障”的普通返回值，而是主动制造租约过期、并发重复提交和授权重放，并将恢复时间与最终状态写入报告。

## 2. 五个场景

### Worker 失联后重新入队

任务先被 Worker 领取并进入 `RUNNING`，随后不再发送心跳。时钟越过租约期限后，回收器把未耗尽重试次数的任务改回 `PENDING`，其他 Worker 可以继续处理。

状态路径：`PENDING -> RUNNING -> PENDING`。

### 重试次数耗尽

任务只允许尝试一次。Worker 失联且租约过期后，不再反复重新入队，而是进入 `FAILED`，避免故障任务无限消耗资源。

状态路径：`PENDING -> RUNNING -> FAILED`。

### 取消期间 Worker 失联

运行中的任务收到取消请求后先进入 `CANCEL_REQUESTED`。即使原 Worker 随后失联，租约回收仍会把任务收敛为 `CANCELLED`，不会错误地重新执行。

状态路径：`RUNNING -> CANCEL_REQUESTED -> CANCELLED`。

### 并发幂等风暴

16 个线程同时提交 64 次相同请求。数据库唯一约束和事务共同保证只产生一个任务 ID、只保存一条任务记录。

这验证的是“并发条件下不重复创建”，而不只是顺序调用两次返回相同结果。

### 审批重放攻击

同一条外部写命令获得一次批准。第一次消费授权成功，第二次再次使用时被拒绝，证明授权具备单次语义，旧批准不能重复利用。

## 3. 如何运行

无需调用 DeepSeek，也无需访问网络：

```powershell
.\.venv\Scripts\python.exe -m corecoder.resilience
```

输出包括每个场景的 PASS/FAIL 和恢复耗时，并生成：

- `evals/reports/resilience/resilience-campaign.json`：便于程序或流水线读取；
- `evals/reports/resilience/resilience-campaign.md`：便于人工复盘和面试展示。

## 4. 代码调用关系

`run_resilience_campaign()` 负责组织场景；每个场景通过真实的 `TaskStore` 或 `ApprovalManager` 注入故障；`_scenario()` 统一比较期望值和实际值；`write_resilience_report()` 固化证据；CLI 根据是否全部通过返回退出码 0 或 1。

## 5. 面试表达

可以简要描述为：

> 我没有只验证正常流程，而是构建了离线故障演练，对 Worker 失联、重试耗尽、取消竞态、并发重复提交和审批重放进行确定性注入；系统依据租约和状态机恢复，并输出机器可读与人工可读报告，当前五类场景全部通过。

## 6. 当前边界

- 使用可控时钟加速租约过期，验证的是状态语义，不代表真实宕机恢复的网络耗时。
- 当前 SQLite 方案定位于单机多 Worker，不等同于跨机器分布式一致性。
- 故障演练目前覆盖控制面，尚未覆盖进程强杀、磁盘写满、数据库锁争用和网络分区。
- 恢复耗时是当前机器的单次观测值，不能直接作为生产 SLA。

下一步应选择一个真实业务闭环，把任务队列、GitHub/CI 状态、审批和审计串起来，而不是继续无边界增加基础组件。
