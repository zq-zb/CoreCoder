# 01 · 仓库级上下文检索

## 解决的问题

小项目可以把文件逐个读给模型，但仓库变大后会出现两个问题：读取大量无关代码浪费 Token；真正关键的实现、测试和配置反而可能被挤出上下文。

原有 `glob` 和 `grep` 仍然保留：它们适合已知文件模式或精确关键字。新增的 `repository_search` 处理的是更早一步的问题——Agent 只知道需求、错误或符号，还不知道应该读哪些文件。

## 实现方式

`RepositoryIndex.build()` 遍历仓库中的文本代码文件，并建立内存倒排索引：一个词出现在哪些文件中。索引主动跳过 `.git`、虚拟环境、构建产物和依赖目录，也拒绝读取超大文件，避免噪声与内存失控。

检索时综合四类信号：

1. 内容词频：查询词在文件中出现得越集中，相关性通常越高；
2. 稀有度：在少数文件出现的词比到处出现的通用词更有区分度；
3. 路径命中：查询词出现在文件名或目录名中时加权；
4. 符号命中：查询直接命中函数、类、接口等代码符号时给予最高额外权重。

每条结果返回文件、最佳行号、周围代码片段、得分和命中原因，因此排序不是黑盒。工具最多返回 20 条、总文本约 15000 字符，防止一次检索反过来淹没上下文。

## 完整调用路径

```text
用户提出修改或排障任务
        ↓
Agent 尚不知道相关文件
        ↓
repository_search(query, repository_root)
        ↓
RepositoryIndex 扫描受支持文件并分词
        ↓
倒排索引召回候选文件
        ↓
路径 + 符号 + 内容词频联合排序
        ↓
返回少量带行号、理由的代码片段
        ↓
Agent 使用 read_file 精读最高排名文件
        ↓
修改代码并运行测试
```

关键代码入口：

- `corecoder/repository.py`：索引、打分和片段选择；
- `corecoder/tools/repository_search.py`：Agent 工具协议与输出预算；
- `corecoder/prompt.py`：要求未知路径时先检索、再精读；
- `tests/test_repository.py`：排序、目录过滤、大小限制、错误输入和输出预算测试。

## 为什么现在不使用向量数据库

当前目标是中小型代码仓库，符号名、错误文本和路径往往具有很强的精确语义。词法索引部署简单、离线可用、结果可解释，也适合内网环境。

它的局限也很明确：无法很好理解“鉴权”和 `authorization` 这类不同词但语义接近的表达；每次调用当前都会重建内存索引。只有量化评测证明这些问题成为瓶颈时，下一步才考虑增量缓存、代码结构图或 embedding，而不是为了堆技术栈直接加入向量数据库。

## 如何验证

当前测试证明：

- 路径与函数符号命中能够排在普通文档之前；
- `.git`、构建目录、二进制和超大文件不会进入索引；
- 空查询、错误目录和无结果都有确定输出；
- 返回结果包含行号和排序依据，并受到上下文预算限制；
- `repository_search` 已进入 Agent 默认工具集。

下一阶段还要回答“检索是否真的提高 Coding Agent 成功率”，因此会增加跨文件任务和 A/B 评测指标。单元测试只能证明算法按设计运行，不能替代 Agent 能力评测。

## 面试表达

我针对 Coding Agent 在中型仓库中盲目读取文件导致 Token 浪费和关键信息遗漏的问题，实现了无外部依赖的仓库级上下文检索。系统通过倒排索引召回候选文件，结合路径、代码符号、词频和稀有度进行可解释排序，并用目录过滤、文件大小及输出字符预算控制资源消耗。后续使用固定跨文件任务集对检索前后的成功率、工具调用数和上下文成本进行量化比较。

## 你学习时只需先记住三句话

1. 问题：仓库变大后不能把所有文件都交给 LLM。
2. 方案：先用本地索引找出最相关的少量文件，再让 Agent 精读。
3. 证据：当前有算法单测，下一阶段还会加入端到端 A/B 评测。
