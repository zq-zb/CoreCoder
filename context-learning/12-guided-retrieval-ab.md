# 阶段 12：guided 检索真实对照

## 1. 实验设置

在同一 Git 提交、同一 DeepSeek 模型、同一数据集指纹和同一上下文策略下，重新运行：

- 基线：`structured-memory+retrieval-off`
- 候选：`structured-memory+retrieval-guided`

任务不提供文件路径，只提供权限故障现象与 `AccessRequest`、`can_access` 符号。两组均只运行一次，因此仍属于端到端冒烟，而不是统计显著实验。

## 2. 真实结果

| 指标 | off | guided | guided - off |
|---|---:|---:|---:|
| 成功率 | 100% | 100% | 0% |
| 隐藏测试 | 100% | 100% | 0% |
| 工具调用 | 15 | 16 | +1 |
| 输入 Token | 27,832 | 30,714 | +2,882 |
| 输出 Token | 1,917 | 1,640 | -277 |
| 耗时 | 19.79s | 18.76s | -1.02s |
| 仓库检索 | 0 | 1 | +1 |

guided 的检索返回 4 个文件，目标实现召回率 100%，相关上下文召回率 75%，检索本身耗时约 41ms。

工具轨迹以 `bash → repository_search` 开始。第一个 Bash 被运行时策略拒绝，没有真实执行；模型收到反馈后改为单独检索。因此 guided 解决了 available 模式中“工具存在但模型不用”的问题。

## 3. 如何解读，而不是夸大

当前只能证明三件事：

1. guided 运行时策略能够让该模型真正覆盖检索链路；
2. 检索结果确实召回目标文件和多数相关上下文；
3. 加入检索没有破坏该次任务的正确性。

不能证明 guided 稳定提高成功率，因为两组都成功且各只有一次。输入 Token 反而增加 2,882，说明检索输出和一次策略反馈具有上下文成本。耗时减少约 1 秒也可能是模型服务波动，不能归因于检索。

## 4. 策略拒绝的可观测性

工具轨迹会记录模型提出的调用，包括被策略拒绝的尝试。为了区分“模型想调用”和“工具真实执行”，评测结果新增 `retrieval_policy_rejections`，汇总报告也记录总拒绝次数。

本次报告生成时该字段尚未加入，因此对比器根据 guided 轨迹中首次 `repository_search` 之前的受控工具调用恢复出 1 次拒绝。未来报告直接使用显式计数。

## 5. 面试表达

真实实验显示 DeepSeek 在工具仅可用时不会主动使用仓库检索。我没有继续加强软提示，而是实现运行时 guided 策略，拒绝检索前的广泛读取，并保证首次检索不能和读取并行。再次 A/B 后，模型在一次策略反馈后调用检索，目标文件 Recall 达到 100%，隐藏测试仍通过。同时我记录策略拒绝和 Token 开销，并明确单次实验不能证明成功率提升。
