# 02 · 检索评测与指标

## 为什么“能够检索”还不够

一个 Agent 调用了检索工具，不代表检索有价值。它可能返回了十个无关文件，随后仍靠遍历仓库完成任务。因此这一阶段把检索过程纳入外部评测，回答两个问题：是否找到了真正需要修改的文件；为了找到它付出了多少上下文和时间成本。

## 当前五个指标

1. `repository_search_calls`：一次任务调用了多少次仓库检索；
2. `repository_search_results`：累计返回多少个候选文件；
3. `repository_context_characters`：检索结果向模型注入多少字符；
4. `repository_search_duration_seconds`：建立索引和排序累计耗时；
5. `repository_target_recall`：案例允许修改的目标文件中，有多少出现在检索结果里。

例如一个案例允许修改 `service.py`，检索返回 `api_client.py`、`service.py` 和 `README.md`，则目标召回率是 100%。如果案例需要同时修改两个目标文件但只找到一个，召回率是 50%。没有调用检索时记为 `n/a`，而不是错误地记为 0%。

## 数据如何流动

```text
RepositorySearchTool.execute()
        ↓ 记录调用、候选路径、字符数和耗时
RepositorySearchTool.stats()
        ↓
CodingAgentEvaluator 在任务结束后读取统计
        ↓ 与 case.json 的 allowed_changed_files 对照
计算目标文件召回率
        ↓
EvaluationResult（单案例）
        ↓
EvaluationSummary（全数据集聚合）
        ↓
evaluation.json + evaluation.md
```

工具可能被 Coding Task 的工作区安全守卫包装。评测器会逐层找到内部真实检索工具，但不绕过安全守卫执行操作；它只在任务结束后读取只读统计快照。

## 安全与并发考虑

- `repository_search` 已加入工作区路径守卫，Agent 不能借检索读取任务目录之外的文件；
- 指标更新由锁保护，多工具并行调用时不会丢计数；
- 统计只保存相对文件路径和数值，不保存完整源码，避免评测报告膨胀；
- 报告仍保留单案例指标，聚合平均值不会掩盖某个任务检索完全失效。

## 当前证据与边界

专项测试已经验证指标能够从被工作区守卫包装的工具传递到评测结果，并正确得到 100% 目标召回率。报告的 JSON 和 Markdown 都会包含聚合指标。

但是 `allowed_changed_files` 只是当前可用的目标文件真值，它不一定包含所有“值得阅读但不应修改”的依赖文件。因此目标召回率衡量的是“关键修改目标有没有找到”，不是完整的信息检索学术指标。下一阶段会在跨文件案例中增加明确的 `relevant_context_files`，分别衡量修改目标与只读依赖的召回效果。

## 面试表达

我没有把新增检索工具本身当作优化完成，而是把检索轨迹纳入 Agent 评测。系统记录检索次数、候选规模、上下文字符量和耗时，并用案例目标文件计算召回率，从而在成功率之外衡量检索质量与成本。指标更新具备并发安全，并通过工作区守卫限制检索范围。

## 你先记住三句话

1. 调用了检索，不等于找对了文件。
2. 召回率证明是否找对，上下文字符量和耗时说明代价。
3. 下一步要用跨文件任务做真正的前后对比实验。
