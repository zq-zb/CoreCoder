# 阶段 08：把缓存行为纳入统一评测

## 1. 针对什么问题

阶段 07 已经实现索引缓存，但如果指标只存在于工具对象内部，项目运行结束后就很难回答：缓存到底有没有命中、索引重建了几次、文件变化是否触发失效。

工业系统中的性能能力必须可观测。否则缓存失效、Agent 每次都创建新工具实例等退化问题，可能长期存在却没有证据。

## 2. 怎么实现

评测器在任务结束时，从 `RepositorySearchTool.stats()` 收集：

- `cache_hits`：直接复用已有索引的查询数；
- `index_builds`：实际读取文件并构建索引的次数；
- `cache_invalidations`：检测到仓库变化后废弃旧索引的次数。

单案例记录原始计数，评测汇总计算整体命中率：

`缓存命中率 = 缓存命中次数 / 仓库检索调用次数`

这些字段同时写入 JSON 和 Markdown。JSON 供程序、趋势平台或 CI 比较，Markdown 供人阅读。

## 3. 顺便解决的维护问题

原先检索指标通过六元组传递，调用方依赖 `metrics[0]`、`metrics[5]` 之类的下标。增加指标后很容易发生错位。本阶段将其改成 `RepositoryEvaluationMetrics`，使用字段名读取，避免“魔法下标”。

报告中的 `Cache H/B/I` 分别表示 Hit、Build、Invalidation。这样每个案例都能看见自己的缓存行为，而不仅是一个全局平均值。

## 4. 如何解释指标

- 首次只检索一次：命中率为 0% 且构建一次，这是正常冷启动。
- 同一仓库连续检索：通常首次构建，后续命中。
- 修改文件后再次检索：应看到失效次数和构建次数增加。
- 调用很多但命中始终为 0：需要检查工具实例是否被反复创建，或仓库是否持续产生临时文件。

命中率不是越高越好。若为了高命中率而忽略代码变化，Agent 会基于旧上下文修改代码，正确性反而下降。

## 5. 面试表达

我没有把缓存优化停留在局部实现，而是将命中、重建和失效指标贯穿到 Coding Agent 的统一评测结果，并输出机器可读 JSON 与人工可读报告。同时用结构化指标对象替代易错的元组下标，使后续扩展更安全。这样可以在 CI 或多轮实验中识别性能退化，也能验证缓存没有以牺牲上下文新鲜度为代价。
