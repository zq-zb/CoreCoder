# DeepSeek 真实评测与改进分析

## 实验条件

- 模型：`deepseek-v4-flash`
- Provider：OpenAI 兼容接口
- 数据集：15 个分层 Coding 任务
- 初始数据集指纹：`ceccdefe45540244`
- Python：3.11.5
- 温度：0
- 验收：隔离工作区、独立隐藏测试、修改范围和工具预算

项目工作区当时存在未提交变更，因此 Git commit 只能标识基础提交，完整实验还必须结合报告中的数据集指纹和当前代码状态理解。

## 主要结果

| 实验 | 通过 | 成功率 | 隐藏测试通过率 | 平均工具调用 | Prompt Token | Completion Token | 平均耗时 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 初始 baseline | 13/15 | 86.7% | 100.0% | 8.27 | 325,095 | 30,149 | 18.52s |
| 收敛提示改进 | 14/15 | 93.3% | 93.3% | 6.93 | 247,118 | 23,853 | 15.78s |
| 可见测试通过后强制停止 | 10/15 | 66.7% | 80.0% | 9.73 | 308,090 | 27,055 | 17.70s |

收敛提示单轮结果相对初始 baseline：Prompt Token 下降约 24.0%，Completion Token 下降约 20.9%，平均工具调用下降约 16.1%，平均耗时下降约 14.8%。但模型存在明显随机波动，不能仅凭一次 14/15 宣称稳定提升。

## 稳定性实验

首次对 `log-secret-redaction` 和 `protected-branch-normalization` 各重复 3 次，仅通过 1/6：前者 1/3，后者 0/3。多次失败时隐藏测试已经通过，但模型继续调用工具直到预算耗尽。

增加“修改后测试通过即强制停止”后，两案例合计提升到 3/6，但完整 15 案例降至 10/15。该策略被判定为失败实验：它能减少部分冗余，却可能在模型完成边界检查前过早结束。

加入已知缺陷契约和预算提示后，`log-secret-redaction` 连续 3 次全部通过。进一步根据工具名称轨迹，把专用文件工具排在 Bash 前，并加入软收敛反馈；`protected-branch-normalization` 三次都完成了修改且不再出现预算耗尽，但只有 1/3 通过隐藏测试，剩余瓶颈转为模型实现质量。

## 实施的通用改进

1. 空模型响应不再被当作成功：自动纠偏一次，连续两次为空则明确失败。
2. 修复型评测必须检测到真实文件变更，避免“无修改、无测试”假完成。
3. 任务提示公开工具轮次预算，并要求修改后测试通过即停止重复操作。
4. 专用文件工具排在 Bash 前，减少把 Shell 当文件浏览器的倾向。
5. 报告新增任务失败原因、状态事件和仅含工具名称的轨迹。
6. CLI 支持 `--repeat`，报告按案例输出稳定通过率。
7. 保留可选强制收敛能力，但不在评测默认路径启用。

## 结论

本轮最可靠的提升不是某一个最高分，而是评测系统能够识别三种不同问题：

- 控制层假成功：空响应或没有修改却显示完成；
- 执行层不收敛：代码正确但工具调用超预算；
- 模型能力失败：完成修改但未覆盖明确边界。

对当前 DeepSeek 配置，简单和中等任务总体表现较好，复杂边界任务存在显著方差。生产场景不应根据单次运行自动写入主分支，应结合候选分支、独立测试、人工审批和有限重试。

## 限制

- 模型名称没有配置可信单价，因此报告不估算费用，不能用 `null` 当作零成本。
- 各版本只完成一轮全量评测；稳定性只针对部分失败案例进行，样本量仍小。
- 当前任务多为小型隔离代码，不能外推到大型仓库。
- 修改提示或工具顺序会改变系统版本；公平对比应继续固定数据集指纹、模型、温度和重复次数。
- 不应通过把隐藏测试内容加入 Prompt 来提高分数，那会造成评测泄漏。
