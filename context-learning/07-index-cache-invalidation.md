# 阶段 07：索引缓存、主动剪枝与变更失效

## 1. 针对什么问题

此前每次 `repository_search` 都会重新读取并分词整个仓库。Agent 在一次任务中通常会连续检索多次，这会重复消耗磁盘 I/O 和 CPU。最初加入缓存后，实测热查询仍需约 1.5～2 秒，说明瓶颈没有真正消失。

原因是 `Path.rglob()` 仍会深入 `.venv`、`.git` 等大型目录，只是在枚举出文件后再跳过。也就是说，过滤发生得太晚。

## 2. 怎么解决

1. 使用可剪枝的目录遍历，在入口处排除依赖、版本库和生成目录。
2. `RepositorySearchTool` 保存最多 4 个仓库索引，并采用 LRU 淘汰，限制内存增长。
3. 每次查询比较文件路径、大小和纳秒修改时间构成的轻量指纹。
4. 指纹不变则复用索引；变化则重建，防止 Agent 修改代码后仍读到旧内容。
5. 用独立锁把指纹检查与重建串行化，避免并发查询重复构建。
6. 暴露缓存命中、索引构建和失效次数，并提供可重复运行的性能基准。

## 3. 本机阶段性实测

在当前 CoreCoder 仓库连续执行 5 次相同查询：首次约 211ms，后续约 65～70ms。该数字受机器与仓库规模影响，因此项目提供 `corecoder-retrieval-cache-benchmark`，不把单次本机结果当作通用结论。

## 4. 为什么不做全局永久缓存

全局缓存容易让多个 Agent 共享可变状态，也可能无限占用内存。当前选择 Agent 工具实例级缓存：生命周期清晰、任务之间隔离，并通过最多 4 个仓库的 LRU 控制资源。

## 5. 面试表达

我先测量重复仓库检索延迟，发现简单缓存后仍然很慢；进一步定位到目录过滤发生在递归遍历之后。随后将扫描改为入口剪枝，并实现 Agent 实例级 LRU 索引缓存和基于文件元数据的自动失效，同时增加缓存命中、重建指标与独立性能基准。这样既减少重复解析，也保证代码修改后检索结果不会陈旧。
