## 1. 为什么 Coding Agent 需要上下文工程

Coding Agent 会不断读取文件、执行命令、接收错误并修改代码。长任务中，测试日志和文件内容会快速占满模型窗口。简单删除旧消息虽然省 Token，却可能丢掉“改过哪些文件、为什么这样改、哪个测试失败”等关键状态。

因此目标不是压缩得越短越好，而是在有限预算内保留完成任务所需的信息。

## 2. 当前三层策略

### 第一层：旧工具输出裁剪

超过阈值后，只裁剪较旧且很长的工具输出，保留头尾信息。最新 6 条消息受到保护，因为其中通常包含当前错误和刚读取的代码。

### 第二层：历史摘要

保留最近的完整调用链，把较早消息变成摘要。切分位置不能落在 `assistant(tool_calls) → tool(result)` 中间，否则 OpenAI 兼容接口会认为协议历史不完整。

### 第三层：紧急折叠

上下文接近硬上限时，只保留结构化摘要和最近调用链。这是防止请求因窗口溢出而彻底失败的最后保护。

## 3. 结构化工作记忆

仅依赖模型自由摘要有不确定性：模型可能漏掉文件路径或错误。`structured-memory` 策略会在模型摘要后追加规则提取的事实：

- 操作过的文件路径；
- 最近错误；
- pytest、passed、failed 等测试信号；
- 最近用户目标。

它不是 RAG。RAG 解决“从外部知识库找什么”，工作记忆解决“当前任务已经发生了什么”。对于现阶段的 Coding Agent，后者更基础。

## 4. 为什么要记录压缩事件

每次压缩都记录层级、压缩前后估算 Token 数和消息数，并汇总：

- 压缩次数；
- 估算节省 Token；
- 每一层触发次数。

这些指标会进入 Agent 评测报告。这样可以比较两个策略是否在保持成功率的同时减少上下文成本。

## 5. 真正的 A/B 对比

- `baseline`：使用模型生成的普通摘要。
- `structured-memory`：模型摘要后追加确定性工作记忆。

两个策略必须运行同一数据集指纹、同一模型和同一代码版本。重点比较成功率、隐藏测试通过率、工具调用数、输入 Token、压缩次数和节省 Token。

如果只在报告中修改策略名称，而 Agent 行为没有变化，就不是真正的实验。当前 CLI 已把策略参数传入 Agent。

## 6. 面试表达

我针对 Coding Agent 长任务中的上下文膨胀与关键信息遗失问题，实现了分层上下文治理：优先裁剪旧工具输出，随后对历史调用链做安全摘要，并在接近窗口上限时紧急折叠。为降低自由摘要遗漏关键状态的风险，我增加了确定性工作记忆，保留文件、错误、测试状态和用户目标；同时记录每层压缩事件，并接入统一评测框架进行 A/B 对比。

## 7. 央国企项目表达侧重点

央国企技术岗位通常更容易认可“业务可落地、运行稳定、过程可控、结果可验收”的项目。CoreCoder 后续应优先强调：

1. 稳定性：超时、熔断、故障隔离、有限时间退出与恢复。
2. 安全性：最小工具权限、目录边界、危险命令控制、敏感信息保护。
3. 可审计：记录谁在何时调用了什么工具、修改了哪些文件、最终验收结果。
4. 可部署：支持内网模型或兼容接口，不强绑定单一云厂商。
5. 可验收：固定数据集、隐藏测试、指标报告和可复现实验版本。
6. 可维护：中文设计文档、错误复盘、测试覆盖和清晰模块边界。

不建议为了简历盲目加入 Redis、LangGraph、向量数据库。只有出现跨进程状态、复杂工作流或大规模知识检索的真实需求时，再引入对应组件。
