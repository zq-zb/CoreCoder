# CoreCoder 量化评估：从“能运行”到“能证明”

## 1. 这一阶段解决什么问题

普通单元测试回答的是“某段代码是否正确”，Coding Agent 评测回答的是：

> 面对一项没有见过的编码任务，Agent 能否在有限时间和工具预算内，修改正确的文件，并通过独立验收？

因此不能只相信 Agent 最后的文字，例如“我已经修复”。评测器必须从 Agent 外部检查最终文件和隐藏测试。

## 2. 一条完整链路

1. 从 `case.json` 读取任务、修改范围、工具预算和验收命令。
2. 把案例工作区复制到临时目录，避免案例互相污染。
3. 为每个案例创建全新的 Agent，避免上下文泄漏。
4. Agent 读取代码、修改文件并运行可见测试。
5. Agent 结束后，评测器独立运行隐藏测试。
6. 对比运行前后的文件哈希，检查是否越界修改。
7. 汇总成功率、工具调用数、失败测试次数、耗时、Token 和费用。
8. 输出 JSON（方便程序比较）和 Markdown（方便人阅读）。

核心边界是：Agent 负责“做题”，Evaluator 负责“监考和判分”。

## 3. 为什么需要隐藏测试

可见测试会给 Agent 修复提示，但只针对可见测试写死代码也可能通过。隐藏测试位于 Agent 工作区之外，覆盖空输入、边界值和跨文件调用等情况，用来验证修复是否真正泛化。

当前数据集包含 16 个任务，覆盖单文件逻辑、字符串边界、多文件调用链、参数校验、长度边界、HTTP 重试、API 分页、路径权限、日志脱敏、多源配置优先级、Webhook 签名、租约临界值、CI 日志分类、受保护分支、批任务幂等和资源权限策略。新增企业边界题采用“可见测试通过、隐藏边界失败”的方式，减少 Agent 只照着公开断言修改的可能。

## 4. 为什么检查文件修改范围

“测试通过”并不代表行为安全。Agent 可能顺手修改测试、配置或无关文件。每个案例通过 `allowed_changed_files` 声明允许范围，评测器直接比较文件系统快照，而不是依赖 Agent 自报。

这会形成两个独立维度：

- 功能正确性：隐藏测试是否通过。
- 行为约束性：是否只修改允许的文件。

## 5. 失败分类的意义

- `agent_failed`：Agent 循环或初始化失败。
- `hidden_test_failed`：修改结果功能不正确。
- `unexpected_file_change`：越界修改文件。
- `tool_budget_exceeded`：虽然可能做对，但过程成本失控。
- `verification_error`：验收器超时或无法启动，属于基础设施问题。

分类后，面试时可以说明：失败不是一个模糊的“没做对”，而能定位到推理、执行边界、效率或评测基础设施。

## 6. 可复现与公平对比

报告记录模型、Provider、策略名、Git 提交、Python 版本和数据集指纹。以后做上下文工程时，可以用同一数据集比较：

- `baseline`：当前完整历史上下文。
- `context-compression`：加入压缩后的策略。

只有数据集指纹一致，两个成功率、Token 和工具调用数才适合横向比较。

## 7. 如何运行

先运行离线演示，不调用 API：

```powershell
.\.venv\Scripts\python.exe examples\evaluation_demo.py
```

只查看真实评测案例，也不调用 API：

```powershell
.\.venv\Scripts\python.exe -m corecoder.eval_cli
```

用 DeepSeek 运行一个案例（会产生 API 费用）：

```powershell
.\.venv\Scripts\python.exe -m corecoder.eval_cli --case calculator-sign --run --strategy baseline
```

确认单案例链路稳定后，再去掉 `--case` 跑完整数据集。

## 8. 面试时可以怎样讲

我没有只用单元测试验证 Coding Agent，而是设计了隔离式任务评测框架。每个任务运行在独立副本中，由 Agent 外部的隐藏测试验收，并用文件快照检查越界修改；同时记录工具调用、失败重试、耗时、Token 和成本。报告带有数据集指纹和代码版本，可用于公平比较不同上下文策略，避免只展示一次成功 Demo。

## 9. 下一步

## 10. 本次开发中的错误记录

### 离线演示长时间不结束

- 现象：静态检查通过，但演示超过 30 秒仍没有报告。
- 原因：可见测试使用了相对模块导入，命令却在项目根目录运行，没有进入隔离工作区；测试失败后，任务运行器继续进入修复流程。
- 解决：测试命令先切换到当前案例的隔离工作区，再执行 `pytest`。
- 收获：测试命令本身也是评测基础设施的一部分。工作目录不明确，会把基础设施故障误判为 Agent 能力不足。

### PowerShell 输出中文乱码

- 现象：程序成功结束，但中文摘要显示成乱码。
- 原因：当前终端捕获编码与 Python 标准输出编码不一致。
- 解决：命令行入口和演示入口显式将标准输出配置为 UTF-8。
- 收获：结构化 JSON 报告不受影响，但可读命令行输出也应该稳定，否则会降低排障效率。

### 项目完整测试误收集隐藏测试

- 现象：当时直接运行项目完整 `pytest` 时，最初 5 个隐藏测试在收集阶段提示找不到案例模块。
- 原因：pytest 默认递归扫描整个仓库；隐藏测试依赖 Evaluator 为单个案例设置的隔离工作区和 `PYTHONPATH`，不能脱离评测器直接收集。
- 解决：在 `pyproject.toml` 中把框架回归测试入口限定为 `tests/`。隐藏测试仍由各案例的 `case.json` 驱动，不是跳过验收。
- 收获：框架测试与 Agent 能力评测是两套不同生命周期的测试，目录和运行入口必须明确分离。

### 策略拒绝后任务仍显示完成

- 现象：`git push` 被命令策略拒绝，但模型随后正常结束，任务报告仍可能是 `completed`。
- 原因：原任务状态机只识别代码修改和测试结果，没有把安全策略拒绝纳入最终状态判定。
- 解决：Tracker 记录策略拒绝事件；只要存在拒绝，最终任务状态就是 `FAILED`，并保存具体原因。
- 收获：Agent 的自然语言结论不是系统事实，控制面必须根据真实工具执行结果决定任务状态。

### Windows 路径测试出现字符串语法错误

- 现象：新增 `C:\` 根目录测试后，Python 在测试收集阶段提示字符串没有闭合。
- 原因：Python 原始字符串不能以单个反斜杠结尾，末尾反斜杠会转义引号。
- 解决：改用普通字符串并把反斜杠写成 `\\`。
- 收获：安全规则经常同时涉及 Python、正则表达式、PowerShell 三层语法，必须分别验证每一层的转义含义。

### 安全能力没有接入主 CLI

- 现象：`CodingTaskRunner` 会拦截需审批命令，但普通 `corecoder` 入口仍使用原始 Bash 工具。
- 原因：早期安全包装器写在 Coding Task 模块内部，其他入口无法复用。
- 解决：把 Bash 安全包装器提升为公共组件，并在主 CLI 默认组装命令策略、审批管理器和审计器。
- 收获：完成一个安全模块不等于产品已经安全；所有实际入口都必须经过同一控制面。

### Docker CLI 存在但无法连接 Engine

- 现象：Doctor 能读取 Docker 版本，但查询镜像时提示无权读取 Docker 配置，并拒绝连接 named pipe。
- 原因：`docker --version` 只运行客户端，不代表当前进程拥有 Docker Engine 权限。
- 处理：不提权、不拉取镜像；保留模拟测试结果，并在文档中明确真实集成测试尚未完成。
- 收获：工具安装、服务运行、当前身份有权访问是三个不同的就绪条件，健康检查应逐步区分。

### apply_patch 输入格式错误

- 现象：开始新增任务存储时，补丁工具提示首行格式非法。
- 原因：发送了占位补丁文本，没有遵循 `*** Begin Patch` 和实际变更块格式。
- 处理：确认工具没有修改文件后，重新提交完整的小模块补丁。
- 收获：工具调用失败后应先确认是否产生部分副作用，再决定重试，不能盲目重复执行。

### SQLite 演示结束后数据库文件被占用

- 现象：任务成功入库并恢复，但 Windows 删除临时目录时提示 `tasks.db` 正被其他进程使用。
- 原因：SQLite Connection 的上下文管理器负责提交或回滚，却不会在退出时自动关闭连接；文件句柄依赖垃圾回收释放。
- 解决：把连接工厂改为显式上下文管理器，在 `finally` 中调用 `close()`；增加操作后立即移动数据库文件的回归测试。
- 收获：事务完成与资源关闭是两个不同概念。在 Windows 上文件锁更容易暴露连接泄漏，成功结果不能代表生命周期正确。

### PowerShell 批量案例校验误运行全套测试

- 现象：批量验证新增案例时目录变量为空，Pytest 没有收到目标文件，因而开始收集项目测试。
- 原因：外层 `ForEach-Object` 和内层目录筛选都使用 PowerShell 自动变量 `$_`，格式化目录前缀时取到了错误对象。
- 处理：立即中断误启动的测试；改用显式 `foreach ($caseIndex in ...)` 变量和明确的目录前缀匹配。
- 收获：测试脚本也需要控制输入范围。命令参数为空时，许多工具会退化为“操作整个当前目录”，因此应在执行前验证目标不为空。

### 数据集扩容后 CLI 测试仍期待旧数量

- 现象：15 个案例均通过数据集校验，但项目全量回归有一项失败。
- 原因：评测 CLI 的回归测试把提示文字中的案例数量固定为 10，扩容时没有同步更新。
- 解决：将断言更新为 15，并重新运行完整测试。
- 收获：规模数字同时存在于代码、测试和文档时容易漂移；真实运行报告应作为最终数据来源，展示性文档需要在发布前统一刷新。

### “测试通过立即停止”降低完整评测成绩

- 现象：为了阻止模型重复调用工具，评测模式在修改后的可见测试通过时强制结束；正式 15 案例成绩反而从 14/15 降到 10/15。
- 原因：可见测试只提供基本反馈，有些任务仍需要模型继续检查任务描述中的边界；过早停止把效率优化变成了质量损失。同时工具轨迹显示，主要失败来自修改前反复使用 Bash 探索，而不是修改后的冗余检查。
- 处理：保留状态机停止能力和单元测试，但从评测默认路径中撤下；依据工具轨迹把读取、编辑、检索等专用工具排在 Bash 前，并明确 Bash 主要用于测试。
- 收获：控制层优化必须同时观察成功率和调用成本，不能因调用数下降就判定更好；失败实验也应保留报告作为决策证据。
