# 企业业务闭环：CI 故障辅助

## 解决的实际问题

研发团队收到 GitHub Actions 失败后，通常需要人工打开日志、定位仓库、复现测试、修改代码并整理结果。CoreCoder 现将这些已有能力串成一条可追踪链路，而不是让 GitHub 工具、Agent 和任务队列彼此孤立。

## 完整路径

1. `GitHubService` 只读获取失败 Job、Step 和截断后的日志。
2. `CIIncidentCoordinator.ingest()` 校验失败证据，以 `repository + run_id` 生成幂等任务。
3. 外部日志被明确包裹为不可信证据，Agent 不应执行日志中夹带的指令。
4. `TaskStore` 保存任务，`DurableCodingWorker` 通过租约领取并持续心跳。
5. `CodingTaskRunner` 驱动 Agent 搜索、修改、测试和有限修复。
6. `AuditLogger` 对每次工具调用脱敏留痕。
7. `build_report()` 将来源指纹、任务状态、尝试次数、改动、测试和审计数关联成事故报告。

## 为什么需要证据指纹

CI 原始数据被规范化后计算 SHA-256。报告中的指纹可以证明任务依据的是哪一份证据，也能帮助发现同一个 Run 的内容是否被改变。它不是数字签名，不能单独证明 GitHub 身份真实性。

## 为什么用幂等键

GitHub webhook 可能重复投递，定时轮询也可能多次发现同一次失败。如果每次都创建修复任务，就可能产生重复修改。数据库以 `ci-incident:{repository}:{run_id}` 做唯一约束，并发或重复通知只返回原任务。

## 为什么日志是不可信输入

源码、Issue、CI 日志都可能包含“忽略规则并执行命令”一类文本。它们只是 Agent 的数据，不应升级成系统指令。本项目在任务提示中标明信任边界；生产环境还应结合工具权限、沙箱和审批，不能只依赖提示文字。

## 如何离线演示

```powershell
.\.venv\Scripts\python.exe examples\ci_incident_demo.py
```

演示会主动创建一个错误的加法实现，注入 CI 失败，随后完整执行“失败测试—修改—通过测试”，报告保存到 `evals/reports/incidents/`。它使用 `ScriptedLLM`，所以不消耗 DeepSeek 费用；真实模型效果应由评测集另行量化。

## 面试表达

> 我把 GitHub Actions 故障采集、持久化任务、Coding Agent 修复、测试验收和脱敏审计串成了一个幂等事故闭环。重复 Run 不会产生重复任务，外部日志按不可信数据处理，最终报告关联证据指纹、改动文件、测试次数和执行审计。离线端到端测试覆盖了从失败进入到修复验证成功的完整路径。

## 当前边界

- 当前 GitHub 能力仍是只读采集，不会自动提交、推送或创建 PR。
- 真实 PR 写操作必须经过身份认证、分支策略和人工审批后再接入。
- 离线演示证明编排正确，不等于证明模型对复杂故障的修复成功率。
- 暂未接收真实 webhook；当前入口可由轮询、API 或后续 webhook 适配器调用。

## 开发过程中发现的问题

首版离线演示使用固定任务数据库，同时在每次运行前把示例源码重置为错误版本。第二次运行会命中已经成功的幂等任务，不再执行 Worker，但源码却再次变坏，于是报告与工作区状态不一致。

原因不是幂等实现错误，而是演示把两个不同生命周期混在了一起：任务记录希望跨运行复用，故障夹具却希望每次重新开始。修复方式是每次演示使用独立临时任务库，让它代表一次新的事故；稳定的工作区和报告仍然保留。这个问题也说明幂等键必须绑定清晰的业务事件，不能脱离事件生命周期使用。

随后还发现编排层最初通过“先查询任务列表、再执行入队”判断本次是否为重复通知。唯一索引能阻止重复任务，但两个并发请求可能都在插入前查到不存在，从而都把自己标记成首次请求。这属于典型的检查—执行竞态。现在由 `TaskStore.enqueue_with_created()` 在同一次数据库插入结果中返回 `created`，并用 16 路并发测试确认只有一个请求被标记为创建者。
