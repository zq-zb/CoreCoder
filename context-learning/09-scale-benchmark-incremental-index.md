# 阶段 09：规模基准驱动的增量索引

## 1. 先测量，再决定架构

缓存命中后仍需扫描文件元数据，仓库变更时则要重新读取和分词全部文件。为了判断是否值得增加复杂度，本阶段构造 100、500、1000、3000 文件的同构仓库，分别测量：

- 冷查询：从零构建完整索引；
- 热查询均值与 P95：缓存命中但仍校验仓库指纹；
- 单文件刷新：只修改一个目标文件后再次检索。

第一轮数据受到 Windows 文件缓存和安全软件干扰，1000 文件结果不够单调。因此又用每个规模 7 次查询复测，没有拿异常单次数据直接做结论。

## 2. 增量刷新怎么实现

索引缓存同时保存上一次仓库指纹。发现指纹变化后：

1. 比较新旧指纹，识别新增、修改和删除路径；
2. 未变化文件直接复用已经完成分词的 `RepositoryDocument`；
3. 只重新读取和解析新增、修改文件；
4. 删除文件不再放入新索引；
5. 用最终文档集合重建轻量倒排表，保证搜索结构一致。

这不是复杂的后台文件监听系统，而是适合本地 Coding Agent 的按需增量刷新：没有常驻监听线程，也不会因为漏掉事件而永久返回旧数据。

## 3. 本机复测结果

| 文件数 | 冷构建 | 热查询 P95 | 单文件增量刷新 |
|---:|---:|---:|---:|
| 100 | 92.65ms | 17.34ms | 18.76ms |
| 500 | 430.18ms | 66.63ms | 66.31ms |
| 1000 | 862.86ms | 148.65ms | 139.84ms |
| 3000 | 2884.72ms | 402.46ms | 410.42ms |

3000 文件下，单文件刷新相对全量冷构建减少约 86% 延迟。此时主要成本变成全仓库元数据指纹扫描和倒排表重组，而不是重新读取全部正文。

这些数字只代表当前机器，项目保留两轮原始报告和最终增量报告，方便复现并观察噪声。

## 4. 正确性保障

测试不只检查“更快”，还验证：

- 修改文件后能搜索到新符号；
- 新增文件会进入结果；
- 删除文件不会残留；
- 未变化文档确实复用原解析对象；
- 增量刷新次数进入统一评测指标。

## 5. 作业过程中的错误

首次创建规模基准文件时，补丁文本末尾被截断并混入无效字符，工具没有写入任何文件。通过 `git status` 和文件存在性检查确认工作区未受影响，随后重新提交完整补丁。这个过程说明编辑失败后应先确认实际状态，不应假设文件已经部分写入。

## 6. 面试表达

我没有直接引入数据库或后台索引服务，而是先建立不同仓库规模下的冷启动、热查询 P95 和变更刷新基准。数据表明 3000 文件时全量重建接近 2.9 秒，因此实现基于文件指纹差异的按需增量刷新，只重读新增或修改文件，并正确处理删除。单文件变更后的刷新约 410ms，相对全量构建降低约 86%，同时用测试保证上下文新鲜度。
