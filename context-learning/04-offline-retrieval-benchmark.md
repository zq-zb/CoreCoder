# 04 · 离线检索基准

## 这一阶段解决什么问题

前三阶段定义了检索、指标和跨文件真值，这一阶段把它们组合成一条可重复执行的离线基准。基准直接使用案例任务文本查询仓库，不调用 LLM，也不产生 API 费用。

## 为什么使用 Recall@K

Coding Agent 通常会读取前几个候选，而不是只读第一名。因此分别统计：

- Recall@1：最节省上下文，只看第一候选；
- Recall@3：允许 Agent 阅读一个很小的候选集合；
- Recall@5：用更多上下文换取覆盖率；
- MRR：第一个相关文件排名越靠前，分数越高。

Target Recall 和 Context Recall 仍分开统计。报告同时记录耗时、索引文件数和每个案例的实际排序，便于定位问题，而不是只显示一个平均分。

## 第一份真实结果

当前两个带跨文件真值的案例得到：

| 指标 | @1 | @3 | @5 |
|---|---:|---:|---:|
| 修改目标召回率 | 50.0% | 100.0% | 100.0% |
| 上下文召回率 | 33.3% | 100.0% | 100.0% |

MRR 为 1.0，平均耗时约 2.2 毫秒。折扣案例的排序是 `checkout.py → test_checkout.py → pricing.py`；分页案例是 `service.py → test_service.py → api_client.py`。

## 如何正确解释结果

前三名覆盖了完整调用链，说明当前检索适合先把小范围候选交给 Agent。折扣案例的修改目标只排到第三，也说明词法检索更容易找到任务描述直接提到的入口文件，不会自动知道深层根因在哪里。

更重要的是，每个案例当前只有三个文件，所以 Recall@3 达到 100% 并不困难。这份报告的价值是建立了可复现基线，而不是证明算法已经达到工业级精度。下一阶段必须加入名称相似的干扰文件和更大的仓库结构，再比较优化前后的数据。

## 如何运行

```powershell
.\.venv\Scripts\python.exe -m corecoder.retrieval_benchmark
```

输出：

- `evals/reports/retrieval/retrieval-benchmark.json`：机器可比较数据；
- `evals/reports/retrieval/retrieval-benchmark.md`：面试和人工复查报告。

## 代码入口

- `corecoder/retrieval_benchmark.py`：运行、聚合、报告和 CLI；
- `tests/test_retrieval_benchmark.py`：案例筛选、指标单调性、报告格式和空数据集行为；
- `evals/reports/retrieval/`：固定基线证据。

## 面试表达

我为仓库检索建立了不依赖模型的离线基准，按跨文件人工真值统计 Target/Context Recall@1、@3、@5、MRR 和检索耗时，并保存逐案例排序用于误差分析。首轮结果显示前三候选可以覆盖现有调用链，但数据集规模偏小，因此我没有直接宣称检索优化完成，而是把加入干扰文件和中型仓库作为下一轮验证条件。

## 你先记住三句话

1. Recall@K 表示前 K 个结果覆盖了多少正确文件。
2. 当前 @3 是 100%，但案例只有三个文件，不能夸大结论。
3. 这份报告是优化前基线，下一步需要增加难度再改算法。
