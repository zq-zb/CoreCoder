# 阶段 15：验证后确定性收敛

## 1. 数据暴露的问题

阶段 14 的单轮追踪显示，Agent 在第六轮已经完成代码修改并通过测试，但第七轮仍把全部历史重新发送给模型，请它生成完成总结。这一轮输入 4,659 Token、输出 179 Token，不能提高隐藏测试结果，只产生自然语言确认。

## 2. 为什么可以由状态机结束

Coding Task 已记录两个版本号：

- `revision`：每次成功修改文件后递增；
- `verified_revision`：测试通过时记录当时的 revision。

只有满足 `verified_revision == revision` 且确实运行过测试，才表示“最新修改已经验证”。因此可以在这个时刻由状态机抛出内部完成信号，结束 Agent 循环，不需要让模型再决定一次。

如果测试通过后又发生编辑，`verified_revision` 会清空；旧测试结果不能验证新代码。这避免了为了节省 Token 而提前结束未验证任务。

## 3. 本阶段改动

正式 `CodingAgentEvaluator` 创建 `CodingTaskRunner` 时启用 `stop_after_verified=True`。这只改变评测闭环的收敛方式：工具执行、文件修改、测试识别、隐藏验收和作用域检查均保持不变。

评测测试新增两个断言：最后一轮必须选择 Bash 测试工具，并且不应存在没有工具选择的额外总结轮。相关状态机测试继续覆盖“修改后验证”“未验证修改失败”和“验证后停止”。

## 4. 取舍

交互式 Coding Agent 可能仍需要面向用户的自然语言总结，因此 `CodingTaskRunner` 的默认值保持关闭。只有量化评测启用确定性停止，因为评测最终由结构化报告和独立隐藏测试给出结论。

这体现了产品模式与评测模式的差异：产品重视解释体验，评测重视可重复的正确性与成本边界。

## 5. 面试表达

> 单轮追踪发现测试已通过后仍有一次 4,659 输入 Token 的总结请求。我复用了任务状态机中的代码修订号和验证修订号，仅在最新修改已有测试证据时让评测确定性收敛，避免把完成判断再次交给模型。同时保留交互模式的自然语言总结，区分评测效率与用户体验。
