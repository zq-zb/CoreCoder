# 阶段 14：单轮 LLM 成本追踪

## 1. 解决什么问题

原评测只能看到整个任务的输入 Token、输出 Token 和总耗时。即使总成本发生变化，也无法判断成本来自首次检索、策略拒绝、大量文件读取，还是最后总结。

阶段 13 的真实复测尤其暴露了这个缺口：总输入 Token 下降，但仍发生了一轮并行调用拒绝。只有聚合数字，无法量化这次拒绝本身浪费了多少。

## 2. 如何实现

Agent 新增 `LLMRoundRecord`，每完成一次真实模型往返就记录：

- 全局递增的轮次编号；
- 本轮输入和输出 Token；
- 模型响应耗时；
- 模型选择的工具名称；
- 本轮被 guided 策略拒绝的工具数量。

记录发生在 LLM 返回后、工具执行前，因此它描述的是模型这一轮真实决策。若执行层拒绝工具，会回写同一条记录的拒绝数量，把“模型提出了什么”和“Runtime 实际允许了什么”关联起来。

## 3. 为什么放在 Agent，而不是 LLM

LLM 层知道 Token 和请求耗时，但不知道工具调用是否被 Agent 的 guided 策略拒绝；Runtime 知道拒绝，却不知道对应请求消耗了多少 Token。Agent 正好位于两者交界处，能够形成完整因果记录。

轮次编号在同一个 Agent 的多次 `chat()` 之间持续递增。评测器会记录任务开始前的下标，只截取当前案例新增的轮次，防止复用 Agent 时混入以前的会话数据。

## 4. 报告与验证

结构化轮次进入评测 JSON，方便脚本计算；Markdown 增加 `LLM rounds` 表，方便人工查看。测试覆盖：

- guided 拒绝与具体轮次正确关联；
- 工具选择顺序被保留；
- 耗时为非负数；
- 多次 chat 的编号连续；
- JSON 和 Markdown 均包含单轮记录。

## 5. 面试表达

> 我没有只记录任务级 Token 总量，而是把成本追踪下沉到每次 LLM 往返，将输入/输出 Token、响应耗时、工具选择和运行时策略拒绝关联起来。这样可以区分“检索正文成本”和“错误工具决策导致的额外往返成本”，为提示策略和上下文预算优化提供可归因证据。

## 6. 首次单轮成本实测

补强“第一轮只能单独检索”后，使用相同 DeepSeek 模型和相同权限调用链案例复测：

| 指标 | 最初 guided | 策略传递修复 | 单独检索约束 |
|---|---:|---:|---:|
| 输入 Token | 30,714 | 26,536 | 23,186 |
| 工具调用 | 16 | 16 | 14 |
| 策略拒绝 | 1 | 2 | 0 |
| 耗时 | 18.76s | 16.94s | 15.86s |
| 成功 / 隐藏测试 | 通过 | 通过 | 通过 |
| 目标 / 上下文召回 | 100% / 75% | 100% / 75% | 100% / 75% |

最终版本第一轮只选择 `repository_search`，输入 1,920 Token、输出 63 Token，没有策略拒绝。随后依次执行 glob、两轮并行读取、编辑、测试和总结，形成七轮完整成本轨迹。

相较最初 guided，输入 Token 单次减少 7,528，约 24.5%。这与拒绝轮次消失、总工具调用减少两次方向一致，但三列均是单次真实运行，不能将全部差异严格归因于提示修改，也不能宣称稳定提升 24.5%。

单轮数据进一步表明，后期测试轮输入 4,503 Token，最终总结轮达到 4,659 Token。原因是每次请求会携带累计历史。下一阶段若继续优化，应研究任务通过后的确定性收敛或历史裁剪，而不是继续压缩仅 694 字符的检索正文。
