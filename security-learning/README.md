# CoreCoder 安全执行与审计

## 1. 解决的问题

Coding Agent 不只是生成文字，它能够读写文件、运行命令和调用外部服务。因此“模型回答正确”与“系统执行安全”是两个不同问题。安全边界必须由确定性代码控制，不能只在提示词里要求模型小心。

## 2. 工具调用审计

Agent 每次实际调用工具后写入一条 JSONL 记录，包括：

- UTC 时间与任务 ID；
- 工具名称和脱敏后的参数；
- 成功、失败或策略拒绝状态；
- 执行耗时；
- 脱敏后的结果预览；
- 原始结果 SHA-256，用于完整性核对。

JSONL 每行都是独立 JSON，适合追加写入、日志采集和故障排查。写入使用线程锁，多个并行工具或子 Agent 不会把记录交叉写坏。

## 3. 为什么既要脱敏预览，也要结果哈希

如果完整保存命令输出，可能把 Token、API Key 或密码写入日志；如果什么都不保存，又无法排障。当前方案保存有限长度的脱敏预览，并保存原始结果哈希：日志不暴露完整内容，但可以判断两次结果是否一致。

常见敏感字段名以及字符串中的 `token=...`、`password=...` 等形式会被替换为 `[REDACTED]`。

## 4. 命令三级风险

### SAFE

本地测试、代码检查和只读 Git 命令，例如 `pytest`、`git status`。Coding Agent 可以直接运行。

### REVIEW

会修改外部系统或主机环境的命令，例如：

- `git push`；
- 创建或合并 GitHub PR；
- 安装 Python、Node 或系统软件包；
- 网络下载。

Coding Task 默认拒绝，需要调用方显式开启授权。

### BLOCKED

高风险动作即使开启普通授权也不能执行，例如：

- 下载内容后直接 pipe 给 shell；
-读取 `.env`、私钥或凭据文件；
-筛选敏感环境变量；
-强制推送远端分支。

规则同时覆盖常见 PowerShell 写法，包括 `Get-Content .env`、面向磁盘根目录或用户目录的 `Remove-Item -Recurse`、`Invoke-WebRequest` 和 `Start-Process`。这是因为安全策略必须匹配真实部署操作系统，不能只检查 Linux 命令。

## 5. 为什么策略拒绝必须让任务失败

模型可能收到“需要审批”的工具结果后直接回复“完成”。如果任务运行器只看模型是否停止，报告会出现假成功。

现在策略拒绝会进入结构化任务事件，并将最终状态设置为 `FAILED`，失败原因明确记录为“被禁止”或“需要审批”。这体现了控制面高于模型输出。

## 6. 当前边界

文件工具已经限制在 Coding Task 工作区内。Bash 命令目前完成了危险行为和外部写操作分级，但还没有构建完整的操作系统沙箱。正则策略适合作为应用层第一道防线，不能替代容器、低权限账户、网络隔离和系统调用级沙箱。

面试时应该主动说明这个边界，而不是宣称“绝对安全”。

## 7. 央国企场景价值

这一能力可以对应内网研发助手的几个常见要求：

- 操作留痕：工具调用能够定位到具体任务。
- 敏感保护：审计日志不直接暴露凭据。
- 权限分级：本地验证与外部变更采用不同授权等级。
- 失败可解释：区分执行错误、策略拒绝和需要人工审批。
- 本地部署兼容：控制逻辑不依赖特定云模型。

## 8. 面试表达

我没有只通过 Prompt 约束 Agent，而是在执行层实现了确定性安全控制。系统将命令分为安全、需审批和禁止三级；外部状态变更默认拒绝，高风险凭据读取和强制推送直接禁止。所有工具调用以并发安全的 JSONL 留痕，并对敏感参数和输出预览脱敏。策略拒绝会使任务明确失败，避免模型文字造成假成功。

## 9. 一次性审批闭环

`REVIEW` 命令现在可以生成审批单。审批具有以下约束：

- 通过 SHA-256 绑定完整命令，批准 `git push origin main` 不能替换成另一条命令。
- 必须记录非空审批人。
- 默认 5 分钟失效，过期后不能执行。
- 批准只能消费一次，防止重放。
- 请求、批准、消费和过期状态会写入原子替换的 JSON 快照。
- 同一条待审批命令重复请求时复用原请求，避免审批单泛滥。

Coding Task 收到未批准的命令时，会在失败原因中返回 `request_id`。外部 UI 或审批服务可以根据这个 ID 展示命令风险；批准后再次运行时，只有完全相同的命令可以通过。

可以运行无外部副作用的演示：

```powershell
.\.venv\Scripts\python.exe examples\approval_demo.py
```

演示只操作内存状态和本地审批快照，不会真正执行 `git push`。

面试时可以把它概括为：审批不是一个可重复使用的全局开关，而是“绑定动作、限时、单次消费、可追责”的最小授权凭证。

## 10. 主程序中的使用方式

普通 `corecoder` 交互入口已经默认启用命令策略和工具审计：

- `.corecoder/approvals.json` 保存审批状态；
- `.corecoder/audit.jsonl` 保存脱敏工具审计；
- `/approvals` 查看当前审批；
- `/approve <request_id> <approver>` 批准一条具体命令。

典型流程：

1. Agent 尝试 `git push`。
2. 工具返回 `Approval required` 和请求 ID，命令没有执行。
3. 用户通过 `/approvals` 核对脱敏后的命令预览与风险原因。
4. 用户输入 `/approve ID 姓名或工号`。
5. Agent 再次提出完全相同的命令时，审批被原子消费并执行。
6. 第三次执行又需要新审批，旧授权不能重放。

也可以退出主程序后使用：

```powershell
.\.venv\Scripts\corecoder-approval.exe list
.\.venv\Scripts\corecoder-approval.exe approve <request_id> --approver <审批人>
```

`.corecoder/` 已加入 `.gitignore`，避免把本地审计轨迹和审批状态提交到仓库。生产环境还应把日志发送到受控日志平台，并设置访问权限、保存周期和完整性保护。
